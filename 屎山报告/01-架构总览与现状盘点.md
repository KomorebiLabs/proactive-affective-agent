# 屎山报告一：架构总览与现状盘点

> 勘察日期：2026-08-16 ｜ 勘察方式：GitNexus 知识图谱（索引与 commit 283d5d0 一致）+ 三路并行代码勘察 + 关键指控人工核实
> 结论先行：**这座屎山的根基不在某个文件写得烂，而在于两次"重构"都是"只加不删"——旧实现从不退役，于是同一套系统里有新旧两套后端并行服役，配置、常量、启动脚本各自繁殖。**

---

## 一、项目是什么

"婉情AI V2.0"——计算机设计大赛作品，主动式桌面情感陪伴智能体。宣称架构：Vue 前端 + Java Spring Boot 业务层 + Python 感知服务 + Python LangGraph Agent，四服务通过 HTTP/WebSocket/Redis 协同。

核心链路：摄像头/麦克风 → 感知服务（MediaPipe AU + openSMILE + Qwen-VL）→ DeepSeek OCC 情感融合 → 五因子干预决策 → RAG 检索 → 流式回复（SSE）+ TTS 语音。

关键事实（均有代码证据）：

- 前端 **WebSocket 直连旧 Python 感知服务** `ws://localhost:8000/ws`（`frontend/src/App.vue:891`），视频帧、音频上传、TTS 播放、心跳全走这条旧通道；只有文字聊天走 Java 8080 的 SSE。**Java 后端名义上是"业务层"，实际上只管一半流量。**
- 旧感知服务 `backend/main.py`（端口 8000）**至今活着**，被启动脚本拉起（`backend/start_all.bat`），并导入 `backend/ai_assistant/core/perception_engine.py`（796 行，BlinkDetector/HeadPoseEstimator/PerceptionEngine）。
- Python Agent（`Agent/main.py`，端口 8001 硬编码于 `main.py:490`）是 LangGraph 状态机，`Agent/src/agent/graph.py:456-495` 装配 7 节点 + 条件路由（silent/subtle/intervene）。
- **Redis 是隐形集成总线**：Java 把对话历史写 `session:{id}:history`（LPUSH + trim 20 条 + 2h TTL，`ChatController.java:118-130`），Agent 从 Redis 拉感知数据（`Agent/src/agent/nodes/collect_perception.py:96`）——跨服务契约全靠散落两边的字符串 key 约定，没有一处集中定义。

## 四、屎山的根基：三次演进，零次删除

git log 讲述了完整的故事：

1. `b961e82` "实现B/S架构重构与MVC分层模式" → 往仓库里**加**了 Java 后端，旧 Python 单体原地保留；
2. `76e19c4` "婉情AI V2 完整重构版本" → 往仓库里**加**了 Agent/ 目录，旧感知服务原地保留；
3. 之后每次修 bug，倾向**再加一份脚本/再加一段兜底**（启动脚本增殖到 5 套、main.py 里长出与 Agent 功能重复的 invoke 代理+规则降级引擎 `backend/main.py:67,123-135`）。

由此派生三大根基性病灶（详细证据见报告二）：

1. **双后端分裂脑**：新旧两套后端都在跑，业务能力（invoke 代理、规则降级、WS 服务）两边各有一份，前端两边的门都进。
2. **约定靠复制不靠引用**：感知权重/阈值在 `Agent/config.py:192-195` 与 `backend/ai_assistant/utils/config.py:79-82` 双份维护；EMOTION_MAP 在 `App.vue:115-121` 与 `appStore.js:157-165` 逐字重复；Redis 客户端在 Agent 内有三份实现。
3. **工程化靠脚本堆**：5 套启动脚本互相漂移（Redis 三种启动方式、venv/venv2.0 检查名不一致、`backend/start_java.bat:3-5` 硬编码作者个人绝对路径）。

## 五、值得肯定的部分（不是全屎）

公允起见，以下设计是合理的，重构时应保留：

- **Agent/src/agent/graph.py** 的 LangGraph 状态机装配清晰，7 节点职责划分得当；
- **Agent/config.py** 把绝大多数环境变量读取收敛到了一处（全 src 散落的 `os.getenv` 仅 3 处）；
- **前端 WS 层**有完整的心跳（25s ping/35s 超时）与断线重连（`App.vue:1101-1145`）；
- **appStore 的 `applyFinalDecisionSnapshot`** 有幂等去重 + 时间戳保护（`appStore.js:120-170`）；
- **Java 侧 MyBatis-Plus + Flyway 迁移**的骨架是朝正确方向搭的（虽然 migration 不全）；
- **LLM 调用**统一走了超时（30s）与规则兜底降级（`fuse_emotion.py:469`），没有裸奔。

## 六、一座屎山的自我修养：风险最高的五个点（预告）

1. `application.yml:12` MySQL root 真实密码随仓库提交（已核实，文件被 git 追踪）；
2. 前端绕过 Java 直连旧 Python 服务，旧服务还带着一套与 Agent 重复的对话引擎；
3. `ChatController.java:65` 自建无界线程池 + 111 行二次注册空回调（注释写着"防止重复回调"，语义混乱）；
4. `App.vue` 1399 行单体，麦克风编解码/音频播放队列/WS 总线/SSE 解析全在组件里；
5. 17 处硬编码 `localhost` 分布在 9 个源码文件——换机、局域网演示、部署三连挂。
